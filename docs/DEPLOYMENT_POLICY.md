## Existing deployment setup and risks

- This working directory has no Git repository or observed CI workflow. No remote, watched deployment branch, GitHub action, Vercel, Netlify or Firebase auto-deploy configuration was found locally. This does not prove an account-level hosting integration cannot exist; hosting was not changed or inspected during this phase.
- Existing deployment is documented as manual ZIP upload to Hostinger. `scripts/package-hostinger.py` creates a sanitized archive; it does not deploy. `scripts/hostinger-build.mjs` creates a MySQL standalone build; it does not upload. Neither was run for deployment in Phase 0.
- Hostinger startup instrumentation can apply MySQL migrations and optionally seed demo data when HOSTINGER_DATABASE_BOOTSTRAP/HOSTINGER_SEED_DEMO are enabled. Therefore never test against a hosted DB or start a development process with production DB_* credentials. Even an apparently harmless server startup can mutate data with those flags enabled.
- lib/database-url.ts prioritizes DB_PASSWORD/DB_NAME/DB_USER over DATABASE_URL. Local processes must clear all DB_* variables and explicitly use a SQLite file, local origin and bootstrap flags false.
- Older README/SHARING/LAUNCH-PLAN/HOSTINGER notes are historical. Their old public tunnel, automatic sharing and deployment steps are not current permission. No cloudflared process was active during the audit. Do not restart a tunnel. Bind local servers to 127.0.0.1 rather than 0.0.0.0.
- Phase 1 integration tests now require an explicit isolated SQLite DB and loopback test URL. Run only from the separate fixture workspace; access tests use a second isolated preview DB.
